# Phase 2: QR Codes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Bitly's QR Codes feature end to end: QR model coupled to links, list/create (2-step)/details/edit/customize pages, styled rendering and downloads, server-side plain images, scan analytics, logo uploads, Home "QR Code" quick-create mode and the link↔QR touchpoints on the Links pages.

**Architecture:** A `qr_codes` row always owns exactly one link (`link_id UNIQUE`; spec §11.3). The encoded content is `{short_url}?r=qr`; the Phase 1 redirect server already records such clicks with `source='qr'`, so scan analytics are the existing stats v2 with `source=qr` forced. Backend keeps repository → service → handler with mocks; frontend keeps TanStack Query hooks and copies the Links list/toolbar/details patterns. Styled codes render client-side with `qr-code-styling` from a `render_customizations` JSON the backend stores opaquely (only `color`, `background`, `error_correction` are read server-side for plain PNG/SVG).

**Tech Stack:** Go 1.25, Gin, sqlx, MariaDB, `github.com/skip2/go-qrcode` (PNG + bitmap; SVG built by hand), testify, mockgen; Next.js 16, React 19, TanStack Query 5, shadcn, `qr-code-styling` 1.9, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-24-bitly-clone-design.md` §5.1 (QR mode), §5.2 (⋯ menu, has_qr filter), §5.3 ("Generate a QR Code"), §5.4 (QR card), §5.6, §6.1–6.4, §11.3. Phase 1 ledger: `docs/superpowers/plans/2026-10-24-phase1-ledger.md` (parked finding carried into Task 1).

## Review Focus

1. Deleting a link that has a QR must remove the QR (FK cascade) and the QR list must not 500 afterwards; deleting a QR whose link has `source='link'` must keep the link; deleting a QR whose link has `source='qr'` must delete the link even if it was redirected or has a custom back-half — Task 3 (`TestQRService_Delete_*`).
2. A `source='qr'` link must never show in `GET /links`, `/links/export` or `/search` counts, while `has_qr=on` on `GET /links` returns only `source='link'` links with a QR — Task 2 (`TestLinkRepository_ListByGroup_HasQR`).
3. A hidden QR (`archived=1`) must still scan: the QR service never writes `links.archived` and the redirect path is untouched — Task 3 (`TestQRService_SetArchived_LeavesLinkAlone`).
4. `POST /uploads` must refuse SVG, anything that is not PNG/JPEG by sniffed content, and files over 5 MB (413); served names are random — Task 5 (`TestUploadHandler_*`).
5. `GET /qr-codes/:id/stats` must answer 404 for another user's QR and must ignore `?source=` (always `qr`) — Task 5 (`TestQRHandler_Stats_ForcesSourceQR`, `_OtherUser404`).
6. `PUT /links/:id {domain_id: 0}` moves the link to the default domain only if the back-half is free there (409 otherwise) and invalidates the old custom-domain cache key — Task 1 (`TestLinkService_Update_DomainZero*`).
